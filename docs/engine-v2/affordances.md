# Engine v2: the affordance directory (the contract W3 and W5 build against)

Status: the contract of workstream W6 ([integration-plan.md](integration-plan.md) §2.5, §5.1, §6). Code:
`lib/v2-affordances` (`@workspace/v2-affordances`). Owner decision 16, verbatim: "It's essential that we keep the
architecture that ensures that every single operation is available to an AI assistant whether embedded or via the
remote AI assistant delegation protocol as well as via the searchable command pallete. There should be a single dynamic
directory of affordances available by context that generates each of those interface surfaces DRYly."

## 1. The rule

Every operation a human or an assistant can perform is **one entry in `DIRECTORY`** (`src/ops/*.ts`), and nothing else
lists operations. Every surface is generated from it:

| Surface | Generated by | Notes |
|---|---|---|
| Embedded assistant | `assistantTools(ctx)` → `{name, description, input_schema}[]` | tool name = id with `.` → `_` (`toolName`, inverse `affordanceForTool`) |
| Remote assistant (MCP) | `mcpTools(ctx)` → `tools/list` entries with annotations and output schema | `ctx.grant` narrows to the credential's permission |
| CLI | `cliCommands()`, `parseCli(argv)` | `<namespace> <verb> --flag value` and `call <id> '<json>'`; flags from the JSON Schema |
| Command palette | `paletteFor(ctx)` → entries with `searchText`, `confirm`, `availability`; `searchPalette` | the app maps entries onto its palette UI |
| UI buttons | `useAffordance(id)` (W6-2, `@workspace/v2-affordances/react`) | `{available, reason, fix, confirm, spends, run(args)}` |
| Server | `defineOp(affordance, handler)` (W6-2) | one Convex function per server affordance plus its internal twin |

The assistant, MCP and the palette all start from **`availableAffordances(ctx)`, the dynamic directory**: every
affordance whose `contexts` include `ctx.context`, whose `caller` the principal satisfies, which the grant allows and
whose own `available()` check does not hide it, with its availability now (unavailable rows keep a reason and a fix
so every surface can say why). `refusal(affordance, ctx, args)` is the same check for one call, used by the server and
by `useAffordance`.

## 2. A declaration

```ts
affordance({
  id: "agent.summon",                  // namespace.verb; unique
  title: "Summon an agent",            // ≤ 60, verb first
  description: "…",                    // ≤ 600, for a model
  tooltip: "…",                        // ≤ 240, for a human
  keywords: ["deploy", "new agent"],   // palette aliases, at least one
  group: "agents",                     // palette grouping
  scope: "game",                       // none | room | game: the room or game in view (app) or bound (credential)
  params: obj({ language, source, requestId: requestId.optional() }),  // zod v4 object (import from "zod/v4")
  result: z.object({ agentId: id, price: z.number() }),
  contexts: IN_GAME,                   // signedOut home room planning live paused ended replay admin
  caller: "seated",                    // anyone signedIn member seated owner admin (not a ladder)
  effect: "write",                     // read | write | destructive
  spends: "energy",                    // optional: energy | aiBudget
  confirm: "summary",                  // none | inline | summary | modal
  runs: "server",                      // server: a Convex function; client: a view operation on the human's layout
  available: ctx => …,                 // optional pure check on GameFacts (energy, pause used, seats)
  surfaces: { except: [...], because: "consent" },  // optional; consent is the only allowed reason
})
```

Rules the parity test enforces (`parityProblems()`, `test/parity.test.ts`):

1. every affordance is reachable from the assistant, MCP, the CLI and the palette in at least one context, unless it
   declares the consent exemption (any other reason is refused and leaves every surface required);
2. every server affordance has exactly one handler, and every public v2 Convex function is one (W6-2, below);
3. the web app calls no v2 mutation or action except through `useAffordance` (W6-2);
4. for every context and caller, the assistant, MCP and the palette offer the same set;
5. ids are `namespace.verb` and unique; text within limits; keywords present; destructive and spending affordances
   confirm; server writes take an optional `requestId` (idempotent retries); schemas convert to JSON Schema.

Model-facing results are wrapped `{untrusted: true, notice, data}` (`wrapResult`, `toolResult`): game strings are
written by players and are never instructions. Rationals travel as `"p/q"` strings. Human reads of objects are free;
each answer carries `bits`, what an agent pays for the same read (spec §3.1, §6.2).

## 3. For W3 (the Convex server)

- Every public v2 mutation or action **is** a `defineOp` (W6-2 publishes it in `@workspace/v2-affordances/convex`);
  there is no other way to make one. `defineOp` validates args with the affordance's zod schema, resolves the
  principal and the context from the game header (a resolver W3 supplies), applies `refusal`, records the receipt
  idempotently by `requestId` (a receipts store W3 supplies over `v2Receipts`) and returns the typed result. Each also
  gets an internal twin that takes a principal, which the assistant and MCP executors call.
- The Convex function kind is the handler's choice (`query` for reads, `mutation` for writes, `action` where the
  sandbox or a model runs: `agent.check`, `agent.summon`, `agent.replace`, `agent.putBack`, `pitch.draft`).
- A new operation is declared here first, in its own small PR or as part of the PR that implements it; W6 reviews it.
- Until W3 lands, `@workspace/v2-affordances/fake` (W6-2) implements every server affordance in memory, so the
  surfaces are tested end to end.

## 4. For W5 (the app)

- No button calls a Convex function: it calls `useAffordance(id)`, renders `reason` when unavailable, and shows the
  same confirmation the palette uses (`confirm`, `spends`).
- The palette's rows are `paletteFor(ctx)`; the hand-written bind tables of v1 have no v2 counterpart.
- View operations (`runs: "client"`) change the human's layout (`v2Layouts` pane params), so a remote assistant
  changes what the human sees and every open client follows. Representation pins live there, not in localStorage.
- The app builds the `AffordanceContext` from its subscriptions: the page's context (room, phase, replay), the
  principal (signed in, member, seated, owner, admin) and the game's cold facts (energy, pause used, seats).
